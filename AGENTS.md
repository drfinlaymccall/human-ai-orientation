# Human AI Orientation

Read CONTROL.md, docs/design-brief.md and CONTRIBUTING.md before substantial changes. The learner outcome is a reviewed, retrievable, portable personal context portfolio and a meaningful next goal. Preserve the bring-your-own-AI, copy/paste, fictional-example and no-JavaScript routes.

Moodle core is unmodified and pinned; do not publish its private runtime configuration or learner database. Use shared content fragments and supported Moodle APIs, preserving IDs, answers, attempts and completion. Additive modules must not erase historic evidence or silently redefine course completion.

Keep design records: need/feedback -> decision -> change -> verification -> remaining questions. Never fabricate conversation quotes, pilot observations, test results or historical commits. Keep private data out of public issues and documentation. Do not approve or send real support replies on Finlay's behalf; only Finlay's explicit approval authorises an exact reply to its intended recipient. Synthetic tests must be labelled and use the capture transport.

Finlay uses `https://orientation.finlaymccall.com` as the project's live development preview. On 25 October 2026 he requested visible changes there so he can see and feel the work. Delivery includes publishing completed, reviewed changes to that site and checking them there, unless he explicitly holds publication. Preserve accounts, saved work, activity history and existing acquisition settings. Owner preview publication lets Finlay inspect new features; it does not establish wording approval, genuine-mail receipt, human-pilot completion or permission to invite others/open broader registration. Record those states separately.

Email credentials are entered directly in Moodle admin settings and remain in the private database. Do not print or commit them. Open registration only after email, recovery, support and operating checks are recorded.

Documentation and current-status upkeep are part of every change. Every plan must name the affected learner/author/operator documentation and CONTROL.md or state why no update is needed. Update those records in the same commit/PR as the change, including verification and remaining limits. Reuse the relevant GitHub issue; create a separate documentation issue only for independently queued work. Never close an issue until its acceptance evidence is linked.

Before merging any PR, follow `docs/operations/claude-pr-review.md`: use the VPS Claude CLI for an independent review of pinned public-source base/merge-base/head and complete material scope, adjudicate findings, test accepted fixes and review the changed candidate. Missing, failed, incomplete or stale review is not a pass. Record a sanitised receipt externally to the reviewed commit; never expose runtime/private learner material. This is a procedural requirement until required GitHub checks/rulesets are independently verified. Workers return bounded patches/evidence; the integrator owns shared publication and final merge readiness.
