# Native orientation progress

The native course section labels are **Introduction** and **Your course**. These names describe the sections without implying that the number of displayed completion controls equals the three core activities. The existing portfolio completion control remains separate within activity 2.

The public course remains available without an account. `/local/orientation/index.php` is **Your course journey**, the private signed-in atlas: it reads the current learner's native Moodle activity completion, suggests the first incomplete core activity and links to every visible activity. It reuses the generated public atlas with native destinations and plain-text current-user states. Manual Pages say **Not yet complete** until marked done; the Lesson can say **Not started**, **In progress** from its own saved timer, or **Completed** from native completion. Selecting an illustrated place reveals its native activity action beside it. Without JavaScript, the same authorised descriptions and links remain a readable list; optional manifest entries without artwork appear in an additional plain list. It creates no second progress database or inferred competency results. The separately gated [optional starting-point check](starting-point.md) stores self-ratings only in native Quiz attempts and renders an explained practice suggestion separately from Continue. Its new saved-rating privacy/help wording requires Finlay’s review before pilot/public exposure. The original three core activities are the suggestion baseline; portfolio practice belongs within activity 2 and retains its separate existing completion control. Optional preparation stays optional. There is no newly invented overall course-completion or mastery award.

The five learner labels, stable slugs, public destinations, current versions, dates, practice outcomes and baseline roles live in `content/course-map.json`. Moodle destinations resolve from the configured course shortname and adopted `course_modules.idnumber`, never a client-provided course/user ID. Existing module IDs, attempts, answers, completion records and completion criteria must survive updates. Page completion remains manual: merely opening a Page does not mark it complete. The context Lesson keeps its native resume/reflection behaviour. Version labels describe current content; they do not pretend to record which edition each learner read. Signing in saves Moodle activity progress, not the portfolio fields: download a private JSON backup and restore it on another browser/device; use Markdown for selective reuse.

## Reproduce and deploy

Use the existing pinned Moodle runtime. This installs an additive repository-owned local plugin and copies the public manifest; it does not modify core, mail configuration, accounts or existing evidence.

```sh
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" python3 scripts/deploy-orientation.py --trial-dir trial/launch-fixture --upgrade
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" scripts/php scripts/configure-journey.php status
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" scripts/php scripts/configure-journey.php configure
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" scripts/php scripts/configure-journey.php check
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" scripts/php scripts/sync-preparation.php
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" scripts/php scripts/sync-journey.php
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" npm run test:progress
ORIENTATION_TRIAL_DIR="$PWD/trial/launch-fixture" npm run test:onboarding
```

The explicit fixture path is important: the default private runtime is `trial/`. For a reviewed deployment, use that runtime deliberately and record the before/after module IDs and successful unchanged-evidence result. Never rerun initial seed/reset tools on the released course. The plugin installer uses Moodle's native `admin/cli/upgrade.php --non-interactive`. Install/upgrade before configuring onboarding; then publish shared content and verify the gateway and progress view. Moodle caches must recognise the new plugin capability and observer.

The shared identity resolver uses stable IDs first. On first adoption it validates an existing private `course.json`, `journey.json` or `preparation.json` module ID against its actual course/type; only without that record may it resolve an unambiguous legacy name. Conflicting identifiers, missing adopted modules, wrong course/type or ambiguous names cause refusal. New Pages receive stable IDs when created. The manifest declares baseline version 1 and its original three core slugs; installer, publishers and overview reject a removed/reclassified original or additional required activity until an explicit completion-policy change is implemented. This protects the practice suggestion baseline independently of Moodle’s untouched course-completion criteria. Display-name changes use Moodle's native rename API. Both publishing tools retain transactions and evidence fingerprints; a changed fingerprint rolls the update back. Run publication twice for an update check. Keep private manifests alongside runtime data; do not publish them to GitHub. A missing adopted activity requires operator review, not automatic recreation under a new ID.

## Session and native navigation

The plugin copies `content/generated/activity-atlas.html` and the scoped `activity-atlas.css`/`activity-atlas.js` into its runtime directory. It never loads public `site.css` into Moodle. Private rendering filters unavailable places, resolves stable native/support links and adds progress/version guidance through DOM hooks. Static generated HTML contains no learner state.

`/local/orientation/state.php` is an observational GET/HEAD endpoint. Its only JSON fields are `state` (`signed-in` or `signed-out`) and the fixed `journey_url` (`/local/orientation/index.php`). It does not require login, redirect, choose a user, enrol anyone, mark progress or change a pending native login destination. It requests Moodle's read-only/no-session-update handling and suppresses its own Set-Cookie headers: a delayed anonymous probe must not replace a newer protected-page/login session. Moodle still resolves identity from its native session; no custom cookie reader is used. Since pinned core retains the user on an expired read-only session, the GET probe separately reads the native session record and mirrors core's timeout and enabled-authentication `ignore_timeout_hook` decision. Expired sessions report signed out unless a native authentication plugin permits continuation; the probe does not refresh or destroy the session. Responses are private/no-store and have no CORS sharing; other methods receive 405. Personal progress remains within the authorised private journey. History snapshots and background tabs hide private journey content before leaving; restoration or a return to a background tab reloads through native authentication, including when another tab has switched accounts.

Supported Moodle `primary_extend` and `extend_default_homepage` hooks add **Your course journey** and **Help**. Dashboard/My courses are removed from primary navigation only for active ordinary orientation learners with no other active course enrolment, retaining staff controls and other-course navigation. Account and sign-out controls remain native. The ordinary login homepage is changed only by the explicit `configure-journey.php configure` command above; `status`/`check` are read-only and `check` exits nonzero until configured. Native intended activity URLs still take precedence. Configuration refreshes only the exact legacy orientation login/course link and removes known obsolete orientation custom-menu links; it preserves acquisition mode, mail settings and unrelated menu/instructions.

The first configuration records `local_orientation/previous_homepage`. To roll back the landing choice, restore that value at Site administration → Appearance → Navigation → Default home page. Original login/menu values are retained privately under `local_orientation/previous_journey_navigation` for selective restoration; do not publish those settings. Keep plugin/native learner records, do not reseed or downgrade Moodle. The optional starting-point check is a separate subsequent unit; this change adds no saved ratings.

## Signup and activity return

New email registrations that begin at a known orientation activity receive a canonical same-site gateway in Moodle's existing `auth_email_wantsurl` preference. The `user_created` observer runs after native email auth saves that preference and before confirmation mail. Other authentication methods, off-site URLs, other courses and unknown modules are left alone. The gateway validates the stable slug, converts native confirmation's POST continuation into a canonical GET, and uses native login/self-enrolment before redirecting to the visible activity. This avoids the pinned Lesson's POST/enrolment parameter-loss edge case without changing core or using a manual GET workaround in tests.

Access requires login, active enrolment (or course administration), the `local/orientation:view` capability and native per-user activity visibility. Guests, suspended/unenrolled users and hidden activities do not gain personal progress. Requests cannot select another user's record. Moodle's private page is not cacheable; no learner status is written to static public metadata.

`tests/progress.spec.cjs` defaults to the isolated `127.0.0.1:18802` fixture. `ORIENTATION_FIXTURE_URL=http://127.0.0.1:18812` selects the independently cloned preview fixture only when its marker, database and private paths match the strict alternate-target guard; see [reproduction](../REPRODUCING.md). Other targets are refused. It uses newly created synthetic learners, native manual completion and Lesson interactions, fresh browser contexts, another account, forbidden/hidden routes, repeated sync, retained evidence and a temporary fixture-only current-version/optional-module display change. It additionally exercises the real session endpoint/headers, ordinary and intended-destination login, native navigation/tour dismissal, staff and other-course access, no-JavaScript atlas reading and sign-out/history return. Its synthetic data and artifacts stay ignored. `tests/onboarding.spec.cjs` covers direct Lesson signup → captured confirmation in another browser → native enrolment → intended Lesson without an explicit navigation repair, plus the native recovery and pilot allowlist checks. These are functional checks, not human learning outcomes or genuine email delivery.


The exact-18812 expiry regression first verifies a fresh authenticated session, seeds a genuine pending Lesson destination and ages the native session timestamp. GET then reports signed out; GET/HEAD preserve the complete native session-record and payload hashes, timestamp, pending destination and browser cookies. This is synthetic evidence, with no production accounts or genuine mail.

Production promotion must follow the [24 October handoff](../releases/2026-10-24-production-handoff.md): preserve the separately deployed My context schema, privacy provider and workspace/navigation first. The installer refuses unrepresented installed schema files or a newer plugin version before copying, and never treats that refusal as permission to delete those files.
